# GameViewの外部IME入力

普段のキーボードを利用し、FlickInputEditTextが標準EditTextのInputConnectionを包んで入力を受け取る。
独自IMEや独自キーボードへの切り替えは必要ない。

## 変更内容

- InputFilterによる入力判定と、その内部からのsetTextを廃止。
- setComposingText / commitTextと、API 33のTextAttribute付き呼び出しを監視。
- 文字列の実際の変化から入力を検出。未確定文字の再送と確定だけの操作は二重判定しない。
- 同じ文字の連続追加入力を検出。削除とカーソル移動は判定しない。
- 変換候補の確定は、すでに判定した変換中の文字として扱う。
- 複数文字の貼り付け等は1回の不正入力として扱い、複数ノートを同時に得点させない。
- ハードウェアキーと、標準Editableを直接更新する経路にも対応。
- IME操作の開始時に曲の判定時刻を取得。文字編集と演出の処理時間を判定時刻へ加算しない。
- 1入力につきスコア・コンボ更新を1回に整理。
- 入力文字列が1 UTF-16単位に達した時に整理（1文字ごとのクリア）。
- 整理はメインスレッドへpostし、IME操作・TextWatcher・外側のbatchEdit中には行わない。
- 標準InputConnectionで変換状態を終了し、文字削除とカーソル変更をまとめて通知。
- IME接続のrestartInputは使用しない。
- 整理前の文字列を覚える再送補正は使用しない。同じ文字の次の入力も判定する。
- 古い接続からの操作と終了通知が新しい接続へ干渉することを防止。
- 予測抑制・学習抑制・全画面編集抑制を要求。学習抑制はAPI 26以降。
- showSoftInputの呼び出しを画面のタッチ開始時に限定し、MOVEごとの呼び出しを廃止。

## 制約

1文字は整理の開始を要求する目安で、厳密な最大文字数ではない。
batchEditが継続中、またはIMEが整理前の文字列を再送する間は、一時的に超えることがある。
IMEが選択範囲・変換終了の通知をどう扱うかはIMEごとに実機で確認する必要がある。

アプリが取得する時刻はIME操作のアプリ受信時点。
IME内のジェスチャー検出や予測処理、IPC、受信前のメインスレッド待ち時間は測れず、
その変動する遅延をアプリだけで完全に補正することはできない。
予測抑制のフラグも、すべてのIMEの内部処理を停止させる保証ではない。

## 診断

デバッグ版でGameViewをポーズすると、Logcatのタグ FlickIme に集計を出力する。
毎文字の文字列ログは出さず、直近128操作の処理時間だけを保持する。

- operations / composing / commit: 操作回数
- maxBuffer: 受信した操作後の最大文字数
- clears: 整理回数
- invalid: 複数文字の編集等による不正入力回数
- recentAppProcessingUs(p95/max): アプリ受信後の編集・判定処理時間（マイクロ秒）

maxBufferが増え続ける場合は、IMEが整理通知後も以前の文字列を送っている可能性がある。
再送補正を外しているため、整理後の実際の再送が二重判定にならないか実機で確認する。
処理時間が短いのに体感遅延が増える場合は、受信前の遅延も調査する。

## 検証

単体テストはFlickTextChangeTest。入力差分、確定時の重複、連続入力、削除、
複数文字入力、Unicode、毎文字クリア後の同一文字入力と即時整理を検証する。
これらはIME接続そのものの実機互換性テストではない。

実機ではGboardとSimejiそれぞれで、次を確認する。

1. 予測入力を有効にした状態で、休符の少ない曲を連続プレイする。
2. 24文字付近・30文字以降で文字抜け、二重判定、遅延の急増がないか確認する。
3. 「あああ」等の連続入力と、未確定文字の確定で判定が増えないか確認する。
4. 濁点、小文字、削除、候補確定、貼り付け時の挙動を確認する。
5. ポーズ・再開、最初から再生、練習シーク、キーボード切り替えを確認する。
6. 予測入力を無効にした状態でも同じ流れを確認し、FlickImeの集計を比較する。
